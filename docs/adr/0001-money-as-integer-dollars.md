# ADR 0001 — 金額用 `i64` 整數元

狀態：已採用（2026-09-06）

## 背景

POS 的每一個數字最後都會變成兩件事：客人手上的找零，與發票上的金額。
兩者只要差一元，前者是客訴，後者是整批被財政部退件。

## 決定

* 所有落地的金額欄位用 **`i64` 整數元**（`core::money::Money`）。
* 需要小數的只有未稅單價與秤重單價，另立 **`Micros`**（1/1,000,000 元），
  只活在計算中間與 `*_micros` 欄位，進 `Money` 時四捨五入一次。
* 資料庫端一律 `INTEGER`（PG 對應 `BIGINT`），由 `tests/ddl_lint.rs` 強制。

## 理由

**為什麼不是「分」。** 這是本專案在對抗驗證後改掉的決策。法源是加值型及非加值型
營業稅法施行細則 §32-1：「銷項稅額＝當期開立統一發票總額÷(1+徵收率)×徵收率」、
「前項銷項稅額，尾數不滿通用貨幣一元者，按四捨五入計算」，銷售額＝總額−稅額。
也就是**稅額與銷售額在法規層就是整數元**，而且「先算稅額再倒扣銷售額」正是官方
用來避免一元尾差的算法。整條下游（發票欄位、金流、現金抽屜、找零）也都只認整數元。

「分」這個刻度同時多餘又不夠：多餘，因為沒有任何下游需要角分，卻讓每一次顯示與輸入
都要乘除 100，而單位錯位是型別系統擋不住、測試也照不到的一類 bug；不夠，因為真正
需要小數的秤重單價 MIG 允許到 7 位。

**為什麼不是 REAL。** IEEE754 無法精確表示 0.1，`2100.0 / 1.05` 會得到
`1999.9999999999998`；而且 `SUM(REAL)` 的結果隨加總順序而異，同一份資料跑兩次報表
可能不一樣 —— 這在稽核上不可接受。

**為什麼不是 TEXT。** SQLite 對 TEXT 做字典序比較，`"9"` 會大於 `"10"`，
`SUM` / `ORDER BY` / `GROUP BY` 全部會錯，而報表是本專案的一級功能。

## 後果

* `split_tax_inclusive()` 用「算稅額再相減」而非各自四捨五入，`sales + tax == total`
  因此恆成立。這條不變量由 `tax_split_identity_holds_over_wide_range` 守住。
* 折扣、服務費、分帳、抹零的分攤全部走同一個 `allocate()`（最大餘數法），
  保證各份加總嚴格等於總額。四個地方共用一個函式，不可各寫一套。
* 換 PostgreSQL 時 Rust 端型別不變，只有 DDL 的 `INTEGER` 要變成 `BIGINT` ——
  這正是 `ddl_lint` 的 `MONEY_SUFFIXES` 清單存在的理由（PG 的 `INTEGER` 是 int4，
  上限 21 億，年度彙總會溢位）。

## 這個決定不可逆

已經用 REAL 寫進資料庫的 `19.999999999999996` 無法還原成使用者當初的意圖值；
用整數元則所有折扣與服務費的中間精度已永久遺失。所以它必須在 M1 就定案。
