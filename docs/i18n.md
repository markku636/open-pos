# 多語系（繁體中文 / English / 日本語）

## 一句話

**畫面文字在前端的字典裡，後端只回代碼與數字。**

不是因為前端比較適合放翻譯，是因為後端不知道看的人要哪一種語言 ——
而它也不該知道。

---

## 兩種字串，兩種做法

### 一、封閉列舉：後端回代碼，前端查表

`內用 / 外帶 / 外送`、稽核動作、出單佇列狀態、網卡不能用的原因 ——
這些以前是後端用中文組好再回傳的，於是英日介面上會出現中文。

修法**不是**在 Rust 裡翻譯，而是後端根本不要產生顯示文字：

```rust
// 以前：struct 同時帶 channel 與 channel_label（"內用"）
// 現在：只帶 channel（"dine_in"），標籤在前端字典裡
```

判斷方式：**這個值有沒有固定的幾種可能？** 有的話它是資料，不是文案。

一個實際的線索：`Sale` 本來就同時有 `channel` 與 `channel_label` ——
代碼一直都在，那個標籤欄位純屬多餘。

### 二、組合出來的句子：帶鍵值與參數，在邊界翻譯

`AppError` 與少數帶數字的訊息走 `msg!`：

```rust
return Err(AppError::Validation(msg!("gateway.hash_key_len", n = k.len())));
```

目錄在 `src-tauri/src/i18n.rs`，一列三語。三條測試盯著它：
必須照鍵值排序（二分搜尋的前提）、三種語言都不能空、
**佔位符在三種語言之間必須一致**（少一個 `{n}`，那個語言的使用者永遠看不到
數字，而其他語言都正常，所以沒有人會回報）。

## 語言存在哪裡

`app_settings` 的 `ui.locale`，**整台機器共用**。

不放 localStorage：收銀機是共用機器，換一台電腦或重灌瀏覽器不該要重設一次，
同店兩台也不該顯示不同語言。

不看 `navigator.language`：作業系統語言跟店家想顯示的語言沒有關係，
而「它自己變了」是使用者最難自行排除的一種問題。

KDS 與掃碼點餐是**獨立的 Vite entry**，不會繼承收銀機的 Provider，
所以它們各自在 `main.tsx` 包一層並讀同一個設定（`get_locale` 在區網上唯讀開放）。
少了這一層，字典查出來永遠是中文，而且不會有任何錯誤訊息。

### 一個已知的限制

`AppError` 的序列化沒有地方可以把 `Ctx` 傳進去，所以語言放在一個 process 全域的
`i18n::CURRENT`。這讓「同一台主機、兩個客戶端各自不同語言」做不到 ——
那件事今天本來也做不到（locale 是單一設定），要做的時候這裡就是要改的地方。

## 前端字典怎麼寫

```ts
cancel: { 'zh-TW': '取消', en: 'Cancel', ja: 'キャンセル' }
```

三種語言**同一行**，用 `satisfies Catalog` 宣告。

分成三份 `zh.json` / `en.json` / `ja.json` 最常見的下場是漂移：有人加了中文鍵
忘了加日文，而那要等到某個日本店員按到那顆按鈕才會被發現。寫在同一行的話，
少一個 TypeScript 當場就紅，根本進不了 commit。

翻譯品質保證不了，但「有沒有翻」可以。

## 日文的坑

### 用詞

日本餐飲業的慣用語，不是字面直譯。直譯出來的日文，日本店員讀得懂，
但會立刻覺得這是外國軟體。

| 中 | 日 | 不要用 |
| --- | --- | --- |
| 結帳 | 会計 | 決済 |
| 桌位 | テーブル | 席位 |
| 關班 | シフト締め | レジ締め |
| 日結 | 日次締め | |
| 找零 | お釣り | |
| 退款 | 返金 | |
| 作廢 | 取消 | |
| 補印 | 再印刷 | 再発行 |
| 已收 | 会計済み | 収受済 |

實際踩過的三種錯：

* **`{n} 伝票`** —— 不合文法。伝票 是名詞不是量詞，日文要「伝票 {n} 枚」。
  這是把中文的「{n} 張單」直接搬進漢字。
* **`収受`** —— 公文用語（文書収受、収受印），不是櫃檯用語。
* **`複`** —— 在日文是黏著語素（複数、複合、重複），不能單獨成詞。

### 版面

日文與英文都比中文長。頂欄有十個分頁，一換行整條工具列就往下擠掉一整列，
點餐區跟著變矮。所以分頁用「伝票」而不是更完整的「伝票・返金」。

**寫字典時就要想版面**，不要等畫面壞了才回頭縮。

## 收據列印：介面語言 ≠ 印得出來

這是最容易想錯的一段。

**介面切成日文，不代表那台印表機印得出日文。** 出單機走的是機身內建字庫，
而字庫由 `CjkEncoding` 決定，那是一個**店家要自己選的設定**，
不能由介面語言推導。

實測（`encoding_rs`，見 `infra::printer::escpos` 的
`neither_encoding_covers_both_languages_so_the_shop_must_pick`）：

| | 印得出 | 印不出 |
| --- | --- | --- |
| **Big5** | 平假名、片假名、長音符 `ー`、「ご注文ありがとうございます」 | **新字體**：`円` `内` `税` `売` `対` `応` `国` `駅` `込` `抜` `当` `焼` |
| **Shift_JIS** | 全部日文 | 繁中菜單字：`麵` `奶` `雞` `糕` `餛` |

直覺會說「Big5 沒有假名所以印不了日文」。**那是錯的** —— 我推錯兩次，
最後拿 `encoding_rs` 實測才問對。Big5 有假名；缺的是新字體，
而那剛好是「円」「内税」「売上」「弁当」，POS 的核心詞彙。

所以症狀不是整排亂碼，是**金額後面的「円」安靜地變成一個空白**。
品名印得出來、收據看起來還是一張正常的收據 —— 比整排壞掉更難被發現。

`encode_text` 會回報編不出來的字。設定頁應該拿那份清單擋下來，
而不是印一堆全形空白給店家看。

## 還沒做完

* `AppError` 一百多處訊息大多還是字面中文（`Msg::literal`）。
  地基已經通了（`msg!` → 目錄 → 依語言 render，有測試證明），
  剩下的是逐處搬。`Msg::is_literal()` 可以拿來做「只能少不能多」的閘門。
* 收據版面（`receipt/templates.rs`）約 62 個標籤還是中文。
* 日文只是語言 —— 稅務邏輯仍然是台灣的 5% 與統一發票。
  要在日本開店還需要消費稅 10%/8% 與適格請求書，那是另一個題目。
