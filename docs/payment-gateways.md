# 電子金流

## 先講結論

**這套 POS 收信用卡的正解，是銀行給你的那台實體刷卡機。**

不是因為我們懶得串，是因為串了也沒有比較好 —— 下面每一節都會說明為什麼。
設定頁上那個叫「不串接（自己抄授權碼）」的選項不是暫時的過渡狀態，
它是被推薦的做法。

| 收款方式 | 這套 POS 的做法 | 需要網路嗎 |
| --- | --- | --- |
| 現金 | 內建 | ✗ |
| **信用卡（店內面對面）** | **`manual` — 刷卡機刷完，把授權碼抄進 POS** | ✗ |
| LINE Pay（掃客人手機） | 已實作簽章層，需 LINE Pay 商家帳號 | ✓ |
| 藍新 MPG（客人用自己的手機付） | 已實作密碼學層，**還需要一個公開網址**（見下） | ✓ |

---

## 這一層真正要解的問題

不是「怎麼呼叫 API」，是**「請求送出去了，但回應沒收到」**。

刷卡失敗不可怕 —— 收銀員當場就看得到，重刷一次就好。真正可怕的是網路在
送出之後、回應之前斷掉：錢在金流商那邊已經扣了，POS 這邊什麼都不知道。
客人走了，而店家要到隔月對帳單才發現多收了一筆，那時已經找不到人。

所以每一次對外請求都是三段：

1. 送出之前先寫一列 `gateway_transactions`（`pending`），**並且 commit**
2. 呼叫 API
3. 回應回來才改狀態。**超時或連不上時改成 `unknown`，不是 `failed`**

`unknown` 是這一層最重要的一個狀態：

| 狀態 | 意思 | 該做什麼 |
| --- | --- | --- |
| `failed` | 明確被拒（餘額不足、卡片無效） | 可以放心重刷 |
| `unknown` | **送出去了，但不知道結果** | **去對帳。不可以當成沒發生** |

把 `unknown` 併進 `failed` 會讓錢無聲地消失。

**重試時交易編號不換。** 金流商認的是我方送過去的訂單號，沿用同一個才是
「不要扣兩次」唯一的保證 —— 換一個新的等於明確地要求對方再扣一次。

---

## 為什麼信用卡不做 server-to-server

藍新（以及所有台灣金流商）能讓你在自己的程式裡直接送卡號的那支 API，
叫「幕後授權」。它的申請文件上有一條沒有例外的規定：

> 若收款商店會經手持卡人資料（如信用卡卡號），即應具備 PCI DSS 認證之
> 合規聲明文件（AOC）且定期更新

一台放在小吃店櫃檯、同時在跑訂單資料庫與廚房出單機的 Windows 電腦，
拿不到 AOC，也不應該碰到卡號。

而那台銀行給你的實體刷卡機**已經是通過認證的裝置**了。卡號從頭到尾不會
經過我們的程式，手續費是你跟銀行談好的，壞了有人來修。POS 這邊要做的
只是記帳 —— 那正是 `manual` 這條線在做的事。

所以 `manual` 是 `PaymentGateway` 的一個正式實作，而不是 if/else 的另一條
分支。其餘所有程式碼只需要認識一種形狀，日結報表也照樣分得出來。

## 藍新 MPG：已經做了什麼、還缺什麼

### 已經做了（`services/gateway/newebpay.rs`）

密碼學層，而且是**可以驗證的**那一半：

- AES-256-CBC + PKCS#7，HashKey / HashIV 直接當 bytes 用（沒有 KDF，
  也不要 base64 decode），輸出小寫十六進位
- `TradeSha` = `SHA256("HashKey=" + key + "&" + 密文 + "&HashIV=" + iv)`，大寫
- `CheckCode` 與 `CheckValue` —— 它們跟 `TradeSha` 是**三件不同的事**，
  樣板的前後順序都不一樣，混淆是這個 API 最經典的整合錯誤
- 回呼驗章（常數時間比較）與解密

這些完全不需要網路、不需要商店代號、不需要簽約，`cargo test` 就能驗。
測試向量用的是**藍新技術文件自己印出來的那組數字** —— 包括一段 448 個
字元的密文，我們算出來的必須一個字元不差。

### 還缺什麼

MPG **不是一支可以用 HTTP client 呼叫的 API**，它是瀏覽器表單轉址。
藍新的規範白紙黑字寫著：

> 禁用以 iframe 或 proxy 或幕後 Http Post 方式等使用 MPG 支付頁

違反會回 `MPG02005 驗證資料錯誤(來源不合法)`。就算我們照 `pay()` 的形狀
硬送，藍新也會擋下來。

而且付款結果是藍新**主動打回來**（`NotifyURL`）的，那需要一個公開網址。
一台在店裡 NAT 後面的電腦沒有公開網址。

要完整跑起來，店家需要自己架一個很小的中繼站（一個 Cloudflare Worker
就夠），它做兩件事：

1. 放一頁自動送出的表單（欄位由 POS 算好上傳，**金鑰不上去**）
2. 當個信箱，把藍新回呼的原始內容存著讓 POS 來拿

POS 端保留金鑰、自己驗章、自己解密，並且用 `QueryTradeInfo` 直接跟藍新
確認 —— 中繼站說什麼都不算數，它不持有秘密，弄丟了也只是重開一個。

**這一段目前沒有實作。** 寫在這裡而不是假裝它不存在，是因為一個
「設定頁上有藍新、按下去卻永遠停在等待中」的 POS 比沒有藍新更糟。

## LINE Pay

用的是 **Offline API v4**，不是線上版 v3。

理由只有一個，但很關鍵：v4 的查詢端點吃的是**我方的訂單號**

```
GET /v4/payments/orders/{我們自己的 orderId}/check
```

也就是說「送出去但沒收到回應」時，我們查得到。
v3 只能用它回給我們的 `transactionId` 查 —— 而那個 id 正好就在我們沒收到的
那個回應裡。對一個把 `unknown` 當成核心狀態的設計來說，這是決定性的差別。

簽章的 HMAC-SHA256 裡 channel secret 出現**兩次**（一次當金鑰、一次當訊息
的開頭），那不是筆誤，是 LINE Pay 的規格。

回應碼 `1172`（重複的訂單號）被歸類為**無法判定**而不是失敗 —— 它的意思是
「這個訂單號我看過」，也就是前一次很可能真的成功了。不認得的回應碼同樣
不當成乾淨的失敗（deny by default）。

## 憑證怎麼存

存在 `payment_gateways.credentials_json`，**沒有加密**。

這句話直接印在設定頁上給店家看，因為假裝它被加密了比誠實地說出來更危險 ——
店家會以為備份檔可以隨便丟雲端。

真正做到的防護是**減少它出現的地方**：

- 設定頁存得進去但讀不回來，回給畫面的只有「有沒有設定」與末四碼
- 診斷包只讀資料表的列數，碰不到那一欄
- `newebpay::Keys` 手寫了一個會遮蔽的 `Debug`，所以它出現在 panic 訊息或
  log 欄位裡也不會印出金鑰

**備份出去的 `.db` 檔等於你的收款權限。** 請把它當成保險箱鑰匙保管。

---

## 對帳

`gateway_transactions` 裡任何處於 `unknown` / `pending` / `authorized` 的
交易都需要人去金流商後台核對。這幾個狀態由 `TxStatus::needs_reconciliation()`
統一判斷，日結時不會被當成收入。

`manually_recorded`（`manual` 這條線收的款）算錢進來了，但日結時要另外拿
刷卡機的紙本簽單對，所以它跟 `captured` 是分開的兩個狀態。
