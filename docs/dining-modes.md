# 多餐飲樣態：吃到飽、單點、飲料店、套餐

## 這份文件的依據

動手前查了 **25 套市售產品、139 筆功能發現**：台灣（iCHEF、肚肚 dudoo、WEIBY 微碧、
Posky、WETOM、雅比斯、快一點）、日本（スマレジ・ウェイター、Airレジ オーダー、
ユビレジ、USENレジ FOOD、Square 日本）、歐美（Square for Restaurants、Toast、
Lightspeed K/L-Series、Clover、Loyverse、Eats365）。

查完之後**推翻了我原本的兩個設計**。那兩個推翻是這份文件最有價值的部分。

---

## 一、被推翻的設計 A：不做「店家層級的營業型態」

原本想做 `stores.dining_mode`（單點 / 吃到飽 / 飲料店），像一個全域開關。

**市場上幾乎沒有產品這樣做。**

| 產品 | 實際做法 |
| --- | --- |
| Square for Restaurants | 沒有營業型態。菜單帶營業時段，「menu picker 依當下時間自動顯示對應菜單」 |
| Toast | 沒有。菜單可用時段 +『時段定價』（同一品項不同時段不同價） |
| iCHEF | **完全沒有吃到飽模式**。只有 per-order 的內用／外帶 |
| Lightspeed K | `Order profiles` 綁在**平面圖**上 —— 最接近「每桌不同模式」的設計 |
| USENレジ | 唯一有真正 **per-TABLE『モード』**（店内／テイクアウト／飲み放題），入座時選 |
| Airレジ | 方案綁在**桌**上：點了「放題プラン」這個商品，那桌就進入吃到飽 |
| Eats365 | 吃到飽是**菜單層級**的物件，「可以同時使用單點與吃到飽兩份菜單」 |
| WEIBY 微碧 | 吃到飽是 **per-order 的 QR 單**，「**同桌不同價**消費者也能點」 |

收斂出來的共識是：**「吃到飽」不是店的屬性，是一桌（或一張單）的屬性。**

理由在 WEIBY 那句話裡最清楚 —— 同一桌可以有人吃到飽、有人單點（大人吃到飽、
小孩單點一份兒童餐）。做成店家開關的話，這種真實情況做不出來。

而「午餐吃到飽、晚餐單點」這種需求，市場一致用**時段**解決，
而 open-pos 的 `availability_rules`（day_mask + 起訖時間）與 `price_rules`
（通路 + 時段 + 優先序）**已經做得到了**。不需要新東西。

## 二、被推翻的設計 B：低消不做成自動補差額

原本想做「低消差額自動變成一行」，並處理它的稅額拆分。

**市場上幾乎沒有產品有低消這個功能。**

* 日本五套（スマレジ／Airレジ／ユビレジ／USEN／Square JP）：**沒有任何一套**有
  ミニマムチャージ。日本的做法是改用固定的 per-head お通し／テーブルチャージ。
* Toast：沒有。文件建議的替代是預付訂金。
* Eats365：沒有。最接近的是 Order Surcharge（可乘人數）與大桌服務費規則，
  但兩者都**不是總額下限**。
* Loyverse：沒有。
* **唯一**打出低消的是台灣的 WETOM，而它是「桌位最低消費**提醒**」——
  提醒，不是自動補一行。

所以低消做成**結帳時的提醒**，不是自動明細行。

這個決定省下的不只是工，是正確性風險：自動補一行差額要處理它的稅額、
要決定它進不進服務費基數、退款時要不要跟著退、分帳時怎麼攤 ——
而市場證明店家並不需要這些。

## 三、核心設計：吃到飽方案

### 3.1 方案本身就是一個商品

這是**所有產品的共識**，沒有例外：

* **Eats365**：「in a typical All You Can Eat setup, only the **representing items**
  are priced」，店員依人數加代表商品
* **Airレジ**：`放題プラン名商品` 是一個普通商品，它的「価格」就是方案價
* **スマレジ**：『プラン』是一筆完整的菜單記錄（単価、税区分、制限時間…）
* **Square JP**：「セット」是一種商品類型，有自己的価格

所以 open-pos 的方案 = **一個既有的 `items` 記錄**。這樣免費得到：

* **人頭分級**（大人／小孩／長者）→ 直接用 `item_variants`
  （Toast 明講 size pricing 就是拿來做這個的；Loyverse 也是 variants）
* **平日／假日、午餐／晚餐不同價** → 直接用既有的 `price_rules`
* 品項排行、銷售統計、稅別、廚房分區 —— 全部自動適用

### 3.2 人頭費是明細行，不是訂單欄位

`compute()` 把 `taxable_amount` 攤到每一行，並保證 **Σ 嚴格等於 grand_total**
（「銷售額＋稅額＝總額」是財政部硬檢核，差一元整批退件）。

所以任何動到錢的東西**必須是一行**。做成 `orders` 上的欄位的話，稅額拆分、
收據列印、分帳分攤、報表統計這四件事每一件都要重寫，而且恆等式會破。

市場也是這樣做的（Airレジ 的方案名商品就是帳上那一行、Eats365 的代表商品、
Loyverse「把服務費做成一個商品」）。

### 3.3 方案內的品項變成 0 元

* **Airレジ**：方案內商品在手持機上顯示「（放）」與 ¥0，只有方案名商品是有價的那行
* **ユビレジ**：方案用「0円商品」做，且有設定決定 0 円商品要不要送進 POS 統計
* **Eats365**：「只有代表商品有價，因為客人只付一次就能取用全部」

### 3.4 中途加人：**提示，不自動改**

這一條是查到才知道的，而且很重要。

**Airレジ 明確不自動調整**，它跳警告：

> 「お客様の人数は変更されますが、お通しの数量は変更されません。
>  お通しの数量を変更する場合は、注文履歴画面から変更してください」

減少人數時警告數量不會跟著減；增加人數時跳出「お通し注文」畫面請店員補點。

這是對的設計：**自動改人頭費 = 自動改金額**，而金額必須是人按下去的。
一個會自己變的帳單，店員在客人面前解釋不了。

open-pos 照做：改人數只改人數，並在畫面上提示「人頭費還是 N 份，要調整嗎」。

## 四、用餐時限：**只提醒，不加價、不擋單**

市場共識非常一致：

| 產品 | 到期行為 |
| --- | --- |
| Square（美／日） | 只有顏色。「Turn Yellow After」「Turn Red After」兩個門檻 |
| Toast | 桌上顯示計時；Toast Tables 顯示進度條 |
| Clover | 預設 90 分鐘後桌子變紅 |
| Lightspeed | 開單過久時時間下方顯示紅色帶 |
| スマレジ | 方案的『制限時間』+『事前通知』→ **推播到手持機**。無自動加價 |
| Eats365 | 進度條綠→黃，超時顯示「OT」 |
| iCHEF | 後台設「滯留」分鐘數，超過在桌上顯示警示圖示 |
| 雅比斯 | 「自動發出提醒」，無加價 |

**沒有任何一套會自動加價。** 擋單的只有兩套，而且都是可選的：
Airレジ 的手機點餐自動停止（可選「全部商品」或「只擋方案商品」），
WEIBY 的 QR 連結到期失效。

時限的歸屬有兩派：綁**桌**（Airレジ L.O.、USEN、Eats365）或綁**方案**
（スマレジ 制限時間）。open-pos 綁方案，因為方案本來就有「120 分鐘吃到飽」
這個語意，而一桌可能同時有兩個方案（Airレジ 對此有明確規則）。

## 五、開桌費 / お通し

兩種模型：

* **商品模型**（Airレジ、ユビレジ、USEN、Eats365、Loyverse）：
  一個普通商品 × 人數。
* **設定模型**（スマレジ）：`テーブルチャージ 円/人`，店家／桌／時段三層可覆寫，
  自動乘上入座人數。

open-pos 走**商品模型** —— 跟人頭費同一個機制，不必再造一個。

**已實作**（`migrations/0012_cover_charge.sql`）：`stores.cover_charge_item_id`
指向一個普通商品，開檯時自動加一行 `line_origin = 'cover'`、數量 = 入座人數。

三個實作上的決定：

* **只存商品，不存金額。** 金額是那個商品的售價，而它已經有規格（大人 / 小孩）、
  平日假日價、稅別、廚房分區一整套。在設定裡再存一份金額就是在等兩邊哪天不一樣。
* **綁「開檯」不綁「開單」。** 同一桌加點時 `table_sessions` 沿用既有的那一筆，
  於是開桌費只收一次。這條寫錯的症狀是收據上多一筆 $150，而客人會當場發現。
* **商品被下架時照樣開桌。** 一台不能帶客人入座的收銀機是壞的；少收的開桌費
  收銀員補點得回來。設定頁在存檔時就擋掉不存在的商品，並在商品事後下架時
  顯示警告。

## 六、套餐

共識模型：**有價的父商品 + 選擇群組**，元件價格獨立於原價。

* **Toast**：父商品的價格是「最便宜組合」的價格，高級選項在 modifier 上加價
* **Lightspeed L**：套餐存**每個元件在套餐內的價格**，與商品原價無關 ——
  「改套餐內的價格只影響套餐，不影響原商品」
* **Square**：セット 有自己的価格，每個選項可帶 `追加料金/ディスカウント`
* **スマレジ**：『コース』有 コースセクション（前菜／主菜／甜點），各自挑菜單

open-pos 已經有 `modifier_groups`（min_select / max_select）與加購價，
**套餐可以直接用它做**：父商品帶價、選項群組必選、高級選項帶加價。
第一階段不新增結構。

---

## 七、收據與廚房單

* **Clover**：「Group identical items into one line」預設開啟 ——
  人頭費點 4 次會收合成一行 ×4。open-pos 的收據要照做，否則吃到飽的單
  會有四行一模一樣的「吃到飽（大人）」。
* **Airレジ**：方案內商品印「（放）」與 ¥0；方案名商品是有價的那行
* **スマレジ**：每個菜單都有「印刷対象伝票」勾選（會計伝票／注文伝票／キッチン伝票），
  所以 0 元的方案內商品可以只印廚房單、不印帳單

## 八、實作順序

| 階段 | 內容 | 依據 |
| --- | --- | --- |
| 1 | `order_items.line_origin`（item / plan / plan_member / cover） | 人頭費是行 → 必須分得出來 |
| 2 | `dining_plans` + 成員；方案綁 `table_sessions` | Airレジ / Eats365 / スマレジ |
| 3 | 方案成員在點餐時變 0 元 | Airレジ「（放）」 |
| 4 | 時限：方案帶分鐘數，桌位圖顏色 + 到期提示 | 全市場共識（只提醒） |
| 5 | 收據收合相同行 | Clover |
| 6 | 低消**提醒**（不自動補行） | WETOM，且市場普遍沒有 |
| 7 | 開桌費 / お通し：商品 × 人數，開檯時自動加 | Airレジ / ユビレジ / USEN / Eats365 / Loyverse |

1–4、6、7 已完成；5（收據收合相同行）還沒做。

## 九、刻意不做

* **店家層級的營業型態開關** —— 見第一節，市場不這樣做，而且做不出「同桌不同價」
* **低消自動補差額行** —— 見第二節，幾乎沒有產品有
* **時限到期自動加價** —— 沒有任何一套市售產品這樣做
* **套餐的獨立結構** —— 現有的 modifier_groups 已經夠，等真的不夠再說
